## 第1段 —— Note を occupantName へ移す(**実装完了 / 2026-09-02**)

> **コードは入った。**`MAP_DATA_VERSION` 10、読み込み時に移行。
> Android 488 件 / PHP 254 件が通過、両フレーバーのビルドも成功。
> **残っているのは実機での取り込みだけ**(下の「移行のやり方」)。

**教職員の氏名はアプリの「備考(`note`)」に入っている。** `occupantName` を足したのは
2026-08-30 だが、**中身は空のまま**で、実際の名前は前からある備考欄に書かれていた。

### 実データで確かめたこと(2026-09-02)

`map-backups/kosenmap_map_1F~5F+Outside+road.json`(version 9、685 ノード):

| | |
|---|---|
| `note` が非空 | **65 件** |
| その中身 | **全部が教職員名か「不在」。自由記述の混入はゼロ** |
| `occupantName` が非空 | **0 件** |

**これで「備考には何が入っているか分からないから移せない」という懸念は消えた。**
実際に全件を目で見て確かめてある。混ざっていれば、工事の連絡が人の名前として
公開ページに出るところだった。

Web の DB が持っていた氏名は 55 件。**アプリの方が 10 件多い。**

### 移行の条件は2つとも満たすときだけ

- `occupantName` が**既にあるノードには触らない。** 備考も残す ——
  両方に入っているのは**想定が外れている合図**なので、黙って片方を消さない
- 移したノードの備考は**空にする。** 同じ名前が2箇所に残る方が悪い

  効くと、氏名を消して備考へ書き直した地点が**次の起動でまた氏名へ戻る**

### 検索には足す、記録には足さない

`matchNodeScore()` は氏名を見る(**先生の名前で部屋を探す動きは元からあった** ——
氏名が備考にあったので引けていた)。

**`isRecordableSearchQuery()` には絶対に足さない。** そちらは
「調べられた語」の記録で、**来場者に見える公開の一覧に人気順で並ぶ**。
足すと個人の氏名が並ぶ。コードにもその旨を書いてある。

### 移行のやり方(実機)

**移行前の書き出しを必ず取っておくこと。** `note` を空にする方向なので、
取り違えると 65 件が消える。版が 10 で保存された後は**もう移行が走らない**。

2. 新しい管理 APK を入れる
3. 起動して地図を開く。**`map_data.json` を読んだ時点で移行が走る**

> **`note` を消してよいのか。** 移行後の `note` は空になるが、**値は
> `occupantName` に残る**ので情報は落ちない。両方に同じ名前が残る方が悪い ——
> 片方だけ直したときに、どちらが正しいのか分からなくなる。

### 移行で分かった、Web 側の突き合わせが曖昧だった理由

**アプリを正本にすれば、そもそも突き合わせが要らなくなる。**

### これで消える作業

- `教員室 管-305` の手入力

## 見つかった不具合 —— API 31 の「おおよその位置情報」(**修正済み / 2026-09-02**)

**API 29〜31 の実機で確認したところ、クラッシュは無かった**(2026-09-02、利用者)。
**ただし API 31 で「広域(おおよそ)/ 詳細(正確)」の選択が出た。**

これは Android 12 で入った仕組みで、`ACCESS_COARSE_LOCATION` と
`ACCESS_FINE_LOCATION` を一緒に要求すると、利用者が**どちらを許すか選べる**。

### 何が起きるか

**「おおよその位置情報」を選ぶと、測位が始まらない。**

`WifiManager.getScanResults()` は `ACCESS_FINE_LOCATION` を要る。
coarse だけ許された状態は「**許可したのに動かない**」で、
いまの画面には `Wi-Fiスキャン権限がありません` としか出ない。

**利用者から見ると嘘に見える。** 許可のダイアログで確かに許可したのに、
「権限がありません」と言われる。**設定画面のどこを直せばよいかも分からない。**

### 直したこと

| # | 作業 | 結果 |
|---|---|---|
| a | **coarse だけ許された状態を、拒否と別に扱う** | `WifiScanPermissionState`(GRANTED / NEEDS_PRECISE_LOCATION / DENIED)。判定は**純粋関数** `wifiScanPermissionState(results, sdkInt)` |
| b | 文言を分ける | `wifiScanPermissionMessage()`。**許可されているときだけ null** を返し、呼ぶ側は null かどうかで分岐する |
| c | どこを直せばよいかを書く | 「端末の 設定 → アプリ → 権限 → 位置情報」。**許可のダイアログは一度断られると二度と出ない**ので、行き方を言わないと詰む |
| d | 呼び出し3箇所を差し替え | `MapFragment` / `AdMapFragment` / `WifiFragment`。**同じ文言が3箇所に散っていた** |

**「広域だけ」と言えるのは、位置情報以外がそろっているときだけ。**
近くのデバイスまで断られているなら普通の拒否で、そこで
「正確な位置情報を選んでください」と言うと**直しても直らない**。検査で固定してある。

アプリ名は文言に書かない —— **来場者向けと管理者向けで名前が違う。**

> **API 33 以上では起きない。** `NEARBY_WIFI_DEVICES` があり、そちらは
> 広域/詳細の別を持たない。**29〜32 の端末だけで起きる** ——
> minSdk を下げたことで初めて届いた範囲で、下げていなければ見えなかった。

> **積み残し**: 33 以上では `NEARBY_WIFI_DEVICES` だけでスキャンできるので、
> `hasPermissions()` が **`ACCESS_FINE_LOCATION` まで要求しているのは過剰**かもしれない。
> ただし要求する権限を変えるのは**実機で確かめてからにする** ——
> 外して動かなくなると、測位が丸ごと止まる。

## 第2段 —— 配信されているかを、両側から見えるようにする(**実装完了 / 2026-09-02**)

**いま「配信が届いているか」を確かめる手段が無かった。**

### 作った直後に、手元で見つかったこと

新しい `km_app_map_release_report()` を手元の設定に対して走らせたら、こう出た:

```
slug=kosen-main  版=10  期限まで26日  アクセスコード=1
  ファイル: あり
  中身: 地点 582 / 教職員氏名 0
```

**アプリの手元の地図は 685 地点・氏名 65 件。** つまり `uploads/` に置かれているのは
**2026-08-25 ごろの古い書き出し**で、`revision` だけが 10 に上がっている。

**疑っていたとおりだった。** そして、この画面が無ければ気づけなかった ——
期限は 26 日残っており、**どの警告にも引っかからない。**

### 分担を決めた(2026-09-02)

| どこで作るか | 何 |
|---|---|
| **Android(管理)** | **ノード・線・指紋・平面図。**地図そのもの |
| **Website(管理画面)** | **イベント(会期・通行止め)。**配信の管理 |

### 2-1. Website 管理画面に配信の詳細を出す(完了)

管理画面「ダウンロード」の帯を、**3つ並べた表**に作り直した。

| 出すもの | なぜ |
|---|---|
| **配信の設定** —— `revision` / 期限 / 残り日数 / チェックサム / アクセスコード数 | 「切れている」しか分からないと、いつ切れるかを見に行けない。**コード 0 は「誰も入れません」と言い切る** |
| **置いてあるファイル** —— 有無・大きさ・更新時刻・SHA-256 | 設定だけ書き換わって**実体が古い**のが、まさにいま見つかった状態 |
| **中身** —— 地点 / 経路 / **教職員氏名の件数** / 指紋 / 地図の版 | 上げ間違いに気づける唯一の数字。**氏名 0 は黄色で出す** |
| **載せているイベント** —— 名前 / 会期 / 会期中・会期前・**終了** | 「終わったイベントが載ったまま」を見つける |

> **「配信中の設定」と「実際に置いてあるファイル」を並べて出す。**
> 片方だけ見せると、いま起きている「設定は新しいのに中身は古い」を見逃す。

| 作ったもの | |
|---|---|
| `km_app_map_snapshot_summary()` | 中身を数える。**純粋関数** |
| `km_app_map_active_event_status()` | 載せているイベントの会期。**純粋関数**(時刻を引数で受ける) |
| `km_app_map_release_file_info()` | 実体を調べる。「無い」と「読めない」を分ける |
| `km_app_map_release_report()` | 3つを1行にまとめる。**DB を使わない**(DB が落ちても配信の状態は見られる) |

### 2-1b. 配信を止める / 消せるようにした(2026-09-03)

管理画面から**停止・再開・削除**ができる。**DB は使わない** ——
止めたいのは大抵、何かがおかしいとき。DB が落ちていても止められる形にする。

| | 何が起きるか |
|---|---|
| **停止** | `api/app-map.php` が 410 を返す。**これから取りに来る端末が受け取れなくなる** |
| **削除** | 設定・地図の実体・**この配信のアクセスコード**を消す。元に戻せない |

> **止めても、既に受け取った端末の地図は消えない。**
> あちらは自分が持っている期限で判断しており、410 は「取得に失敗した」としか扱わない
> (`MapDownloadClient` を読んで確かめた)。
> **ここを書いておかないと「止めたのに使われている」と見えて、
> もう一度止めようとして設定を壊す。** 画面にも同じことを書いてある。
> 配り終えたものまで取り上げたいなら、**期限を縮めて配信し直す**しかない。

決めたこと:

- **期限は触らない。**「止める = 期限を今にする」でも同じ動きになるが、
  **元の期限が失われる** —— 再開したいときに、いつまでのつもりだったのか分からなくなる
- 削除は**アクセスコードも一緒に消す。** 地図だけ消すと**行き先の無いコード**が残り、
  入れた人には「地図が見つかりません」としか出ない(`TEST1` で実際に起きた形)
- 削除は**配信 ID を打たせる。** チェックボックスだと、押し慣れた場所を反射で押して消える
- **設定を先に書き、ファイルは後で消す。** 逆にすると、書き込みに失敗したときに
  「設定は残っているのに実体が無い」状態になる
- 止めた配信も報告には載せる。**消えたように見えると探しに行けない**

### 2-2. Android 側でも配信の期限を見る(完了)

- `mapDeliveryStatus()` / `mapDeliveryMessage()` を**純粋関数**で追加し、
  設定「マップ設定 > 配信の状態」に版・期限・残り日数を出す(**7日を切ると目立つ**)
- **残り12時間を「あと1日」と言わない。** 最終日に「まだ1日ある」と読ませると、
  更新の機会をそのまま逃す。切り捨てて「今日まで」と言う
- 期限切れの画面に**理由**を足した ——「会期が終わったため配信は終了しました。
  **通信の問題ではありません。**」言わないと、電波を探して読み込み直すことになる
- **管理ビルドでは隠す。** あちらの地図は手元の原本で配信ではない。
  出すと常に「まだ受け取っていません」と表示され続けて嘘になる

### 2-3. イベントを Website で作れるようにする(完了)

**Website 側にはイベントの編集画面が既にあった**(`admin/map-events.php`、
会期・通行止め・臨時の地点・臨時名称)。足りなかったのは**アプリへ渡す道**。

**採った形: 配信のときに1回だけ差し込む**(`src/scripts/publish-events.php`)。

```bash
docker compose exec -T web php scripts/publish-events.php          # 調べるだけ
docker compose exec -T web php scripts/publish-events.php --apply  # 差し込む
```

> **配る瞬間に DB を見る作りにしない。** `api/app-map.php` が DB に依存すると、
> **DB が落ちた日に地図そのものが配れなくなる。**
> 会期中にそれが起きたら、来場者は地図を1枚も受け取れない。

| 決めたこと | 理由 |
|---|---|
| **1件にまとめる** | Website は複数のイベントを重ねられる(工事の最中に高専祭)。アプリが適用するのは1件だけで、**重ね合わせた結果がまさに「いま効いている規制」** |
| **会期の終わりは一番早いものに合わせる** | 遅い方に合わせると、**終わった通行止めが残って通れる道を「通れません」と言い続ける** |
| **開始は入れない** | Website 側で「いま有効」と判定済みのものだけが来る。入れると同じ判定を2度することになり、時計のずれで食い違う |
| **版(`revision`)を1つ上げる** | 上げないと `haveRevision >= revision` で本体が返らず、**差し込んだのに誰にも届かない**(一番気づきにくい壊れ方) |
| **イベントが無ければ空で上書き** | 「イベントが無い」と「差し込まない」は別。残すと終わった通行止めが効き続ける |
| 対応づけられなかったものは**数えて出す** | ノードを作り直すと Web 側の指定が静かに外れる |

> **数える前に畳む。** overlay は通行止めの線を**両方向**持っている
> (向きが保証されないため、あちらはわざと2本入れている)。
> 畳まずに数えると、落ちた線がすべて2件に見える —— 検査がこれを捕まえた。

> **アプリ側のイベント編集は残してある。** Web が正本になっても、
> 会場で通行止めを1つ足したい場面は必ず出る。**消すと現場で詰む。**

## 第3段 —— 配備を1コマンドにする(**実装完了 / 2026-09-03**)

`deploy-to-host.ps1` のあとに `host-setup.ps1 -Fix` を**忘れると壊れる**。
実際に「設定の保存だけ失敗する」「地図を送れない」を起こした。

### 1つのファイルに融かさない

**`deploy-to-host.ps1` が、転送に成功したら `host-setup.ps1` を呼ぶ。**

| なぜこの形か |
|---|
| `host-setup.ps1` は**単独でも使う** —— `-Fix` を付けずに「調べるだけ」。1本に融かすと、**配備しないと点検できなくなる** |
| 判断は `host-setup.sh` 1本のまま。**ロジックを2つ持つと、片方だけ直されて食い違う**(これは元から明文化してある方針) |

| # | 作業 | 結果 |
|---|---|---|
| 3-1 | 転送成功後に `host-setup.ps1 -Fix` を呼ぶ | 完了 |
| 3-2 | composer を入れ直す | **やり方を変えた**(下記) |
| 3-3 | **`-NoSetup`** で従来どおり「置くだけ」 | 完了 |
| 3-4 | `-WhatIfOnly` では呼ばない | 完了(そこへ届く前に exit する) |

### 3-2 は「毎回」ではなく「変わったときだけ」にした

プランには「composer.json / composer.lock が**転送物に含まれていたら**渡す」と
書いていたが、**`src/` を丸ごと送っているので常に含まれる。** そのまま実装すると
**配備のたびに `vendor/` を作り直す**ことになる。途中で失敗すれば
**サイトが動かない状態で残る** —— 配備のたびに賭ける類のものではない。

**`composer.lock` の中身をホストと突き合わせ、違うときだけ入れ直す。**
変わったのに入れ直さないと「ホストだけ古い依存」が静かに残るので、
「何もしない」も選べない。

### 終了コードを3つに分けた

| 値 | 意味 |
|---|---|
| `0` | 全部成功 |
| **`2`** | **転送は成功したが、後片付けに気になる点** |
| `1` | 転送そのものの失敗 |

**ファイルはもう置かれている。** ここを 0 で返すと自動実行が「全部問題なし」と読み、
1 で返すと「配備が失敗した」と読まれて、**置けているファイルまで疑うことになる。**
どちらとも違う結果であることを、値そのもので言う。

## 配信中の地図に、アクセスコードを出すようにした(2026-09-03)

**コードを知っているのはリリースを実行した人だけ**だった。設定ファイルには

- **照合は `hash` で行う。** `code` を見て通す経路は作らない

  空欄だと「読めないのか、設定が古いのか」が分からない

| # | 作業 | 結果 |

### 列が無い状態でも壊れないようにした

SQL は**コードの配備とは別に、利用者が流す**もの。順番が決まっていないので、
決め打ちで書くと**流す前に同期した人のところで「不明な列」で落ちる。**
`km_map_nodes_has_split_name()` で在るときだけ読み書きする。
**地図の入れ替えが途中で止まるのが一番困る。**

移行 SQL は既存の行を「最後の空白で切って」埋めるが、**これは推測でしかない。**
正しい分かれ目はアプリが持っており、次の同期で上書きされる ——
埋めるのは、同期までの間に画面が空欄だらけにならないようにするため。

### 4-3 —— 読み取り専用にはしない

プランには「見る画面に変える」と書いたが、**イベントの重ね合わせ(通行止め・
臨時の地点)はこの画面でしか作れず、そちらは同期の対象外で消えない。**
読み取り専用にすると、**会場で通行止めを1つ足す手段が無くなる。**

代わりに、既に入れてある警告帯で「地点と経路の正本は管理アプリ」と言い切っている。
氏名の欄は readonly のまま。

### 4-5 —— 受け渡しは条件が満たされれば自然に消える

適用の可否は `氏名(アプリ) >= 氏名(DB)` で決まる。第1段の移行でアプリ側が
**65 件**になり、DB の 55 件を上回るので、**配信し直した時点で条件が満たされる。**

ただし案内の文面が古かった ——「Website から書き出してアプリへ取り込む」が
既定の手順のように読めた。**いまはそれが逆流になる**(Website の方が10件少なく、
同名の地点を当てられない)。**アプリでの移行を先に案内し、書き出しは戻し道**に降ろした。

### 5-1 —— 古い端末でも端まで描く

`enableEdgeToEdge()` は版で分けずに常に呼ぶ。**版によって見た目が変わると、
片方でしか出ない崩れを作ることになる。**

余白の入れ方は場所で分ける:

| どこ | 何を入れるか | なぜ |
|---|---|---|
| ツールバー | **上だけ** | 背景がステータスバーの裏まで伸びて、今までと同じ見た目になる |
| 中身 | **下と左右** | 上も入れるとツールバーの下にもう一段の隙間ができる |
| 引き出し | 上下 | アカウント画像が時計に潜り、最下段が押せなくなる |

**キーボードとナビゲーションバーは足さない。**大きい方を採る ——
キーボードが出ているときバーはその裏に隠れており、足すと余分に空く。

**切り欠き(ノッチ)も避ける。**横向きで左右に食い込む端末があり、
そこにボタンが来ると押せない。

### 5-2 —— R8 で一番危ないのは Gson

**フィールド名がそのまま JSON のキー。**難読化されると `a` / `b` になり、
**保存済みの地図が丸ごと読めなくなる。**配信パッケージの形も変わってサーバーと噛み合わない。

Gson に渡す型だけを名指しで keep した(パッケージ丸ごとでは縮小の意味が消える)。
**`Stored…` の受け皿を忘れないこと** —— 旧形式を読むためだけの型で、
コードから名前で参照されないので**使われていないように見えて真っ先に消される。**

確かめ方は mapping.txt ではなく、**リリース APK の DEX に名前が残っているか**を見た:

```
occupantName / pathLossExponent / startNodeUuid / rssiByBssid /
expiresAtMillis / activeEventUuid / closedLineKeys / txPowerAtOneMeter
→ 8件とも DEX に在る(改名されていない)
```

R8 が1件止めた: `org.slf4j.impl.StaticLoggerBinder` が無い。
Logto SDK が slf4j 経由でログを出す作りで、実装を入れていないので
**「実装なし」に落ちるのが正常。** `-dontwarn` で承知していると言っておく。

> **R8 が効くのはリリースビルドだけで、単体テストは縮小前を見ている。**
> 「テストは全部通るのに、配ったアプリだけ落ちる」形の壊れ方をする。
> **リリース APK は必ず実機で1回、地図を読み込むところまで確かめること。**

### 5-3 —— `neverForLocation` を付けられないぶん、正面から説明する

あの印は「スキャン結果から位置を割り出さない」という宣言で、付けると
OS が結果から位置に繋がる情報を削る。**測位そのものが成り立たなくなる。**

代わりに、**OS の許可ダイアログの前に**アプリ自身の言葉で3つとも言う:

1. 周囲の Wi-Fi の**電波強度を読む**
2. **校内での現在地の推定**に使う
3. **どこへも送信しない / GPS は使わない**

3つ目を落とすと「位置情報を集めるアプリ」に見える。
**断る道も残してある** —— 断っても地図は見られる(測位が動かないだけ)。

**3画面が同じ入口(`requestScanPermissions`)を使う。**散らすと、
片方だけ開示を出さずに権限を求める形になりうるが、
**画面上は何も変わらないので気づけない。**

### 5-4 —— 3つが同じことを言っている状態を保つ

`lib/legal.php`(正本)/ `Old/docs/play-data-safety.md` / `LocationDisclosure.message()`。
**1つでもずれたら、ずれた方が間違い。**

**位置情報は「収集しない」で申告する。** Play の「収集」は端末の外へ出すことを指し、
Wi-Fi の測定値も推定した現在地も送っていない。送るのは「訪れた地点の名前」
(ランキング用・任意)だけで、座標でも測定値でもない。

```
入れない場合 アカウント画像 [48,127]   一般向けマップ [84,576]
```

**「念のため入れておく」が一番やってはいけない類のもの** ——
画面は壊れず、ただ不自然に空くだけなので気づけない。

### 3. 位置情報の開示が、画面に戻るたびに出ていた

断った人は移動のたびに同じ説明を読まされていた。

**同じ起動のあいだは一度だけ**にした。断った人にも次の起動では出す ——
断ったまま二度と出ないと、**測位が動かない理由に辿り着けない。**

## 第6段 —— 保留していたものを開ける

### 6-1. User-Agent を記録する(**実装完了 / 2026-09-03**)

`km_admin_log` に `user_agent varchar(255) NULL` を足した。
**`ALTER` はアプリの DB 利用者に無い**ので、移行 SQL は**配備利用者が流す**:

```bash
docker compose exec -T mariadb sh -c 'exec mysql -uroot -p"$MARIADB_ROOT_PASSWORD" kosenmap' \
  < src/scripts/migrate-admin-log-user-agent.sql
```

**流さなくても動く。** 列が無ければ記録も表示もしないだけ
(`km_admin_log_has_user_agent()` が在るかを見る)。
**決め打ちにすると、流す前は記録そのものが全部失敗する** ——
監査の記録が静かに止まるのが一番困る。画面には「まだ記録していません」と出す。

| 決めたこと | なぜ |
|---|---|
| **長さで切る**(255、末尾に「…」) | 上限の無い自由文字列は、長い UA で INSERT ごと落ちる。**切れた値を完全なものと思って読むと端末の判別を誤る** |
| **生のまま出さない**(`Android Chrome` などに畳む) | 150字超えを並べると表が読めなくなり、**隣の IP まで読まれなくなる**。全文は `title` に置く |
| 当てにいかない | 見当が付かなければ先頭だけ出す。**間違った端末名を出すより、分からないと言う方がよい** |

> **順番に意味がある。** Edge は Chrome を名乗り、Chrome は Safari を名乗る。
> 細かい方から見ないと、全部 Safari になる(検査で固定してある)。

> 1:1 の別表にする案は採らなかった。**結合が1つ増えるだけで、消すときも面倒。**

### 6-2. アカウントの削除(**本番で確認済み / 2026-09-03**)

| a | 後片付け | `lib/account-delete.php`。**1回の取引で**5表から消し、アバターの実体も消す |

#### 消す対象を挙げ漏らさないための検査

`user_id` を持つ表は5つ —— `km_map_ranking_users` / `km_app_settings` /
`km_user_profiles` / `km_chat_reads` / `km_app_presence`。

`check.php` が **`lib/` の全ファイルから `CREATE TABLE` を拾い、`user_id` を持つ表を
一覧と突き合わせる。** 最初は5本だけ名指しで読む形にしていたが、それでは
**そのファイルに書かれた表しか見つけられない** ——
検査が通るのに漏れている、という一番たちの悪い形になる。
全部を見るようにしたら **`km_app_presence` が見つかった。**

#### 監査の記録だけは行を残す

`km_admin_log` は**誰かを落として行は残す。**

行ごと消すと、**都合の悪い操作をしたあとにアカウントを消せば証跡が消える。**
落とすのは**名前・ID・接続元 IP・端末の名乗り**の4つ。
行ごと消す運用にするなら `KM_ACCOUNT_DELETE_PURGES_AUDIT` を true にする
(**運用者が決めること**)。

> **名前と ID だけでは足りない。** 当初は2つしか落としていなかったが、
> IP が残っていると**時刻と併せてその人を指せる。**
> プライバシーポリシー7に「この記録から個人を特定することはできません」と
> 書いてある以上、**文書と実装が食い違っている状態**だった。

#### 実地の確認で見つかった —— 削除の記録に、消えた人の名前が残る

捨て垢での削除は成功したが、タイムラインにこう出た:

```
Test が削除されたアカウントの情報を片付けました
```

**後片付けが名前と ID を落とした「あと」に、削除の記録を書いていた。**
`km_admin_log_record()` は実行者を `$KM_USER` から取るので、
消した本人がまだサインイン中である以上、**匿名化を免れた1行が必ず生まれる。**

- **消した本人はもう画面を見ていないので、自分では気づけない。**
  利用者がタイムラインを見て指摘した
- **順番では直さない。** 「先に記録すれば UPDATE が拾う」は、
  行を足す順を1つ入れ替えただけで静かに戻る
- `km_admin_log_record()` に第4引数 `$anonymous` を足し、**呼ぶ側が明示する。**
  既定は `false` —— 既定で匿名にすると、普段の管理操作から実行者が消えて監査にならない
- 匿名の記録には**接続元 IP も端末の名乗りも入れない**
- webhook 経由(`api/logto-webhook.php`)は `$KM_USER` が居ないので既定のまま。
  **そちらに残る IP は Logto サーバーのもの**で、消えた人のものではない

**直す前に消した行は、コードを直しても片付かない。**
`src/scripts/fix-admin-log-deleted-actor.sql` を配備利用者が流す(何度流してもよい)。

#### 署名を必ず確かめる

この口は**インターネットに開いている。** 確かめずに受けると
「この利用者が消えました」と誰でも名乗れる ——
**他人のランキングと設定を消せる口**になる。

- `logto-signature-sha-256` の HMAC-SHA256 を `hash_equals` で比べる
  (`===` だと**先頭から何文字一致したかで処理時間が変わる**)
- **鍵が未設定なら何も受け付けない。**「鍵が無いから素通し」にすると、
  設定し忘れがそのまま穴になる
- 本文は**そのまま**署名に掛ける(json_decode してから作り直すと、
  キーの順序や空白が変わって合わなくなる)
- 知らないイベントは **200 で返す**(エラーにすると Logto が再送を繰り返し、
  ログが埋まって本当の失敗が見えなくなる)
- 後片付けに失敗したら **500**(Logto が再送してくれる。200 を返すと二度と機会が来ない)

#### 前提が違っていた —— Account API に削除は無い(2026-09-03)

当初は「**Logto の Account center で利用者が自分を消し、webhook で後片付けする**」
つもりだった。**その道は無かった** —— Account API に削除の口が無く、
本人のトークンで自分を消すことはできない(利用者が実測)。

**Management API の `DELETE /api/users/{id}` を、こちらが代理で呼ぶ**形に変えた。

| | |
|---|---|
| 入口 | `account.php` の「アカウントを削除する」(開かないと見えない場所に置く) |
| 本人確認 | `km_logto_account_verify_password()` —— **パスワード変更と同じ判定**(2箇所に書かない) |
| 消す口 | `km_logto_management_delete_user()`。**GET とは別の関数**にしてある |
| 後片付け | `km_account_delete_data()` |

**順番が決まっている: こちらのデータが先、Logto が後。**
逆にすると、Logto の削除だけ成功して後片付けが失敗したときに
**もう誰のものか分からない行が残る**(`user_id` しか手がかりが無く、Logto から引けない)。
この順なら、Logto 側が失敗しても「データが消えたアカウント」が残るだけで、
もう一度実行すれば片付く。**見えない残骸を作らない。**

## 第12段 —— 表示調整の「文字」が効いていなかった(**実装完了 / 2026-09-05**)

利用者の指摘: **ノードの大きさは変えられるのに、文字の大きさが変えられない。**

そのとおりだった。つまみは出ていて、動かせば表示も `100% → 150%` と変わり、
`localStorage` にも残る。**ただ、その値を読む所がどこにも無かった。**
`labelSize` は `DEFAULTS` に在るだけで、`app.js` にも `map-style.js` にも
`tuning.labelSize` を読む行が1つも無い ——「効かない」のではなく「繋いでいない」。

### なぜ地点と同じようにできないか

| | 大きさを持っているのは |
|---|---|
| 地点 | **JS**(`nodeBox()` が SVG の半径を計算する) |
| 文字 | **CSS**(ラベルは Leaflet の tooltip。`.km-label` の `font-size`) |

だから地点は「マーカーを作り直す」だけで変わるが、文字は作り直しても
同じ字で出てくる。**CSS 変数(`--km-label-scale`)を動かす**形にした。

- `map-style.js` に `labelScale()`(値を係数にする)と `applyLabelScale()`(CSS へ渡す)
- **`style="…"` は書かない。** `setProperty` は CSSOM の API なので CSP に掛からない
  (種類の色を DOM のプロパティで設定しているのと同じ)
- 呼ぶのは `app.js` の**読み込み時**と、表示調整が変わったとき。
  読み込み時にも呼ぶのは、調整パネルを出さない編集画面でも通すため
- 地図の上の字は**まとめて**効かせる(地点の札・建物名・経路の長さ・通行止めの ✕)。
  一部だけだと、大きくしたときに釣り合いが崩れてかえって読みにくい

> **0 を書かれると地図の字が全部消える。** `localStorage` は閲覧者の手元にあり、
> 手で書き換えられる。`labelScale()` はつまみの範囲(50〜200%)へ丸めてから返す。

### `check.php` に足した見張り —— つまみと読む側の対応

**同じ壊れ方を二度作らない。** `map-style.js` の `DEFAULTS` から鍵を拾い、
どこかで `tuning.<鍵>` として読まれているかを見る。つまみだけ足して読む側を
書かなければ落ちる。今回の `labelSize` は、この検査があれば最初に捕まっていた。

> アプリ側(`MapDisplayTuningPanel.kt` の「文字サイズ」)は最初から効いている。
> **範囲だけ違う** —— アプリ 80〜260%、Website 50〜200%。今回は揃えていない。

**在る列だけ読む形は崩していない** —— 移行 SQL は配備利用者が別に流すので、

| | |
|---|---|
| `lib/map-data.php` | `transfer_group_id AS transferGroupId` を返す(在るときだけ) |

> **出入口は接続IDだけで結ぶ**(アプリと同じ)。「玄関」という名前は建物ごとに

> **この直しだけでは通らない場合がある。** 出入口ノードに接続IDが入っていなければ、
> アプリでも Website でも繋がらない(アプリで通っているなら入っている)。

検査は**2つの文脈で確かめた** —— 手元の作業ツリーと、

### 先に直したこと —— 同じ知らせを毎日送っていた

頻度の話をする前に、**上げると壊れる作りになっていた。**

見つかったものは**直すまで毎回見つかる。** 再起動が要る状態は再起動するまで続くので、
毎回送ると**同じメールが毎日届く。**読まれなくなり、
本当に新しい知らせが来たときには開かれていない ——
`docker` のパッケージを「未適用」と数えないようにしたのと同じ理屈を、
自分の送信側でやっていなかった。

送るのは3つの場合だけにした(`/var/lib/kosenmap/` に前回の中身を覚える):

1. 前回と**中身が変わった**とき
2. 変わっていなくても **7日**たったとき(忘れないための念押し)
3. `--heartbeat`(月に一度。**沈黙を「正常」と解釈させない**)

> **送れてから覚える。** 先に覚えると、送信に失敗した回で「送った」ことになり、
> 次からは「前回と同じ」で黙る —— 一度の取りこぼしが**永久の沈黙**になる。
> **直ったら忘れる。** 覚えたままだと、同じ問題が再発したときに黙ってしまう。

**2本とも同じ作法にした。** 片方だけだと挙動が食い違い、
「こちらは毎日来るのにあちらは来ない」を故障と読み違える。

これで**頻度を上げてもメールは増えない** —— 頻度は
「どれだけ早く気づきたいか」だけで決められるようになった。

### メールに載せる件 —— 素のままでは送らない

**バックアップには `.env` と `config/*.local.php` が入る。**

Gmail の 25MB 上限にもいずれ当たる(いまは十数 MB でも、uploads は増える)。

そこで `--attach` は:

1. `.env` の **`BACKUP_PASSPHRASE`** で暗号化してから付ける
   (`openssl enc -aes-256-cbc -pbkdf2`)
2. **合言葉が無ければ添付しない。** 黙って素で送らず、その理由を本文に書く
3. 大きすぎれば添付しない(上限の判断は **PHP 側1箇所**。2箇所に置くと食い違う)
4. **合言葉はメールに書かない** —— 同じ経路に鍵と錠を流したら意味が無い
5. 送り終えたら、web から見える置き場から**消す**

> 既定は添付なし。**置き場から取る**のが普段の形で、添付は「外にもう1部置く」ため。

- `logrotate` も一緒に仕込む(週次・8世代)。
  **古い記録のために新しい記録が書けなくなる**のが一番まずい
- 週に一度(日曜 2:40)の便りに `--attach-logs` を付けてある(2026-09-07 に月1から変更)。

### 通知と適用を分ける

2. **Logto は管理画面のゲートそのもの。** `auth_request` が Logto に依っているので、

### 残り: 他のイメージの固定

`certbot` / `boky/postfix` / `nginx:alpine` / `mailpit` はまだ動くタグのまま。
**こちらでは版を決め打ちできない**(手元でホストの実物を見られない)ので、
ホストで次を実行して、出てきた行を `compose.yaml` へ貼ること:

```bash

```

digest で固定する形(`image: nginx@sha256:…`)を出す。**タグより強い** ——
タグは打ち直せるが、digest は中身そのものを指す。

### 2つの見方を分けてある

| 種類 | 何が分かるか |
|---|---|
| `release` | **新しい版が公開された**(Logto の GitHub リリース)。人が読める版番号 |
| `digest` | **同じタグの中身が入れ替わった**(`latest` のような動くタグ) |

**混ぜない。** 前者は「上げるかどうか」の判断で、後者は
「気づかないうちに上がりうる」という警告 —— 打つ手が違う。

### 通知の作法

- **変化が無ければ送らない。** 毎日届くメールは読まれなくなり、
  本当に上がったときにも気づかれない
- **月に1度だけは必ず送る**(`--heartbeat`)。「何も来ない」は
  「更新が無い」とも「仕組みが壊れた」とも読める。**沈黙を「正常」と解釈させない**
- **宛先は `.env` の `MAIL_ADMIN_TO`。** ソースに書くと、担当が替わったときに
  誰も気づかないまま前任者へ飛び続ける
- **送れなければ 0 で終わらない。**「送ったつもり」が一番危ない

```bash

sudo /opt/kosenmap/scripts/host-updates-setup.sh --fix    # 仕込む
```

**配備の対象に足した**(cron から呼ぶので、ホストに置いてある必要がある)。

### 停止判定のフェイルクローズを緩めた

`km_logto_user_is_suspended()` が `readonly` で失敗したら **`default` で1回だけ試し直す**。

**読み取り専用の M2M は Logto では作れない。** Management API リソースは `all` 一つだけを持つ。

### 座標の落とし穴(実測)

名前で一致する点から当てはめを測ると **x 0.697 倍 / y 0.94 倍**と縦横で比が合わず、
残差が最大 83px 残った。**同じ図面なのに比が合わないのは切り取り方が違うため**で、
この式を採ると手で置いた位置の差ごと焼き付く。**画像を揃えて倍率 1 にする方が正しい。**

一方 `scaleY` が負で offset が 1122 という結果は本物 —— Web は Leaflet の `CRS.Simple` で
**緯度が上へ増える**のに対し、アプリは画面座標で **Y が下へ増える**。
**反転を忘れると地図が上下逆さまになる**(建物が対称に近く、一見それらしく見える)。

**消す方向の間違いは取り返しがつかない。**

### `allow-*.conf` の並び順

`include /etc/nginx/km/allow-*.conf;` は**グロブ**。`allow-admin.conf` の末尾に
`deny all;` があり、**その後ろの `allow` は効かない**。グロブは辞書順で、
`-`(0x2D)は `.`(0x2E)より小さいので `allow-admin-home.local.conf` が先に来る。
**この名前を変えないこと。**

## Android を minSdk 29 へ下げた(2026-08-30)

**33(Android 13、2022年8月)は狭すぎた。** 33 を要求していた理由は
`NEARBY_WIFI_DEVICES` ただ1つで、12 以前は `ACCESS_FINE_LOCATION` でスキャンできる。
`WifiScanController.requiredPermissions(sdkInt)` を純粋関数として切り出し、
**版を引数で受けて両側を検査**している(実機を2台用意しないと確かめられない類のもの)。

29 で止めたのは、Wi-Fi スキャンの回数制限(2分に4回)がこの版から入っており、
それより前は挙動が別物になるため。

lint が見つけた問題は1件だけ —— `ScanResult#getWifiSsid` は API 33 から。
版を見てから触り、古い端末では非推奨の `SSID` を使う。**手で探さず lint に列挙させた。**
